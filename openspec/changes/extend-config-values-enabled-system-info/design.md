## Context

The reference `config_logging()` helper is a bespoke, hand-maintained bridge between a site-specific YAML schema (`console`/`file`/`elastic`/`dynatrace`/`extraAttributes`, each with `isEnabled`/`minLevel`) and `lgr`. It:

- builds `lgr::AppenderConsole`/`AppenderJson`/`lgrExtra::AppenderElasticSearch`/`lgrExtra::AppenderDynatrace` by hand,
- attaches two custom `LayoutJson` instances (one for ElasticSearch, one for Dynatrace) that each use a **function-valued** `transform_event` argument plus a static `transform_event_names` map (only the Dynatrace one is in scope for this change - see below),
- computes a **dynamic** ElasticSearch index name per call via `glue::glue("qa-logs-{Sys.Date()}")` wrapped in a closure (out of scope - see below),
- injects system metadata (host name, container id, R version, current script path, a deployment-tool release id) via `lgr::FilterInject`, computed once at config-apply time,
- honors per-appender `isEnabled: false` to skip wiring a sink entirely (used e.g. to keep ElasticSearch/Dynatrace disabled on dev but enabled on qa/prod via environment-layered config).

`lgr`'s native `version: 1` config (`R/config.R`) already supports naming `lgrExtra::AppenderDynatrace` etc. via `class: pkg::ClassName`, and already supports function-valued arguments - but **only** in two specific slots: a logger's `exception_handler`, and filter entries (`validate_filters_field`/`resolve_filters_field`/`validate_function_value`/`resolve_function_value`). A `LayoutJson`'s `transform_event` argument is an ordinary constructor arg (`instantiate_component()` in `R/config.R:839`) and is passed through `do.call(ctor$new, args)` as a literal YAML-parsed value - there is no path for it to become a `ref:`/`code:` function. Reproducing the reference Dynatrace layout (which uses `transform_event = lgrExtra::transform_event_dynatrace`) is the acceptance test for this gap.

**ElasticSearch is out of scope (see proposal "Why").** `lgrExtra::AppenderElasticSearch$new(conn, index, ...)` needs `conn` to already be a live ElasticSearch connection object (`elastic::connect(host)`), not a host string and not a function `lgr` calls later - unlike `index`, which `lgrExtra`'s own docs confirm accepts either a `character` scalar or a `function`, fitting the generalized function-value mechanism cleanly. Building `conn` from primitive config values is deferred to a future change to `AppenderElasticSearch` itself (in `lgrExtra`), which should accept the primitive connection arguments (e.g. `host`) directly so `conn` becomes an ordinary constructor argument requiring no new `lgr`-side mechanism at all.

There is also no way to say "this appender is defined but currently switched off" - you either include it in `appenders:` or you don't. The reference config's `isEnabled` flag exists specifically so ops can toggle a sink via environment-layered config values without restructuring the YAML tree (`isEnabled: ${ELASTIC_ENABLED:-false}` for instance). Native `lgr` config has no equivalent primitive.

Finally, `config_system_variable_injection()` (the reference implementation's system-metadata helper) is itself just syntax sugar over `FilterInject`: it computes a handful of runtime values once - `hostName`/`containerId` (`Sys.info()`, Docker-file detection), `rVersion` (`R.Version()`), `scriptFile` (a ~100-line helper trying RStudio's API, then `commandArgs()`, then `sys.calls()`) - and constructs a plain `FilterInject` from them, attached (imperatively, hardcoded) to the root logger's first appender. The deployment-tool release id is the one exception: it's just `Sys.getenv("RELEASE_ID")`, already fully expressible today as `"${RELEASE_ID:-}"` on a plain `FilterInject` - no new lgr feature is needed for that part.

## Goals / Non-Goals

**Goals:**
- Make `transform_event` (and any other constructor argument that legitimately needs a function value) expressible via the existing `ref:`/`code:` forms, for **any** component argument - not by inventing a new syntax, but by reusing the current filter/exception_handler machinery for the general case.
- Add a first-class `enabled` key (default `TRUE`) on component definitions (`layouts`/`filters`/`appenders`) and on logger definitions, so a component can be declared present in YAML but inert - the natural target for `${VAR:-false}` interpolation.
- Produce a real, tested, native-`lgr` equivalent of the console/file/Dynatrace portion of a real production config (same layout/transform/metadata injection) to serve as the acceptance proof and as living documentation (`vignette`/example) for anyone migrating off `config_logging()`. ElasticSearch is excluded (see below).
- Document the recommended pattern for environment-layered configs explicitly as "merge before you call `read_config()`" (e.g. via the `config` package, or plain `modifyList()`), since that stays out of `lgr`'s remit.
- Provide a built-in, declarative way to inject standard runtime metadata (`hostName`, `rVersion`, `containerId`, `scriptFile`) - the one part of `config_system_variable_injection()` that a plain `FilterInject` + `${VAR}` interpolation genuinely cannot express - via a new `FilterInjectSystemInfo` class, without adding any new config-grammar concept.

**Non-Goals:**
- Reimplementing `config`-package-style environment layering (`default:`/`qa:`/`prod:` merging) inside `lgr` itself.
- Preserving 1:1 wire compatibility with the reference `config_logging()`'s YAML shape (`console`/`elastic`/`dynatrace` keys, `isEnabled`/`minLevel` naming) - the goal is proving the *native* `version: 1` format can express the same behavior, not making the old shape a valid `lgr` config.
- Changing how `FilterInject`'s values are computed (still literal at config-apply time) - dynamic-per-event metadata injection is unaffected by this change.
- Generalizing "call this function now and use its return value as a literal" as a config-grammar feature (e.g. extending `ref:`/`code:` to mean "invoke immediately"). That would give `ref:`/`code:` two different meanings depending on which key they're attached to (a *function to be called later* by `transform_event`/`exception_handler`, vs. a *value to compute now* for something like `hostName`) - exactly the "multiple ways to do the same thing" ambiguity to avoid. `FilterInjectSystemInfo` sidesteps this entirely by being an ordinary component class, not a config-grammar extension.
- Reproducing ElasticSearch support (appender or dynamic index) in the acceptance fixture, and extending `AppenderElasticSearch` to build its own `conn` from primitive arguments - deliberately deferred as follow-up work in `lgrExtra`, out of scope for this change.

## Decisions

**Generalize function-valued arguments by widening `instantiate_component()`'s arg pass, not by inventing a new schema shape.**
Every component arg value already flows through `instantiate_component()` before being handed to `do.call(ctor$new, args)`. Any arg that is a `list` containing a recognized function-value shape (`{ref: ...}` or `{code: ...}`, the same two forms already validated by `validate_function_value()`) is resolved through `resolve_function_value(..., is_filter_context = FALSE)` before being passed on. A bare-string arg is **not** treated as a function reference (unlike filters) to avoid breaking existing configs where a plain string constructor arg happens to match a loaded function's name - only the explicit `{ref: ...}`/`{code: ...}` mapping form opts in. This keeps the change additive and non-breaking: existing configs have no reason to pass a mapping with a `ref`/`code` key as a literal arg value today.
*Alternative considered*: a new dedicated syntax (e.g. `!!ref` YAML tag). Rejected - `read_config()` treats YAML/JSON as plain data (see `@section Safety`), and introducing custom YAML tags would require a non-standard parser and break the "config is data, not source" guarantee for tools that don't know the tag.

**`enabled: false` removes the component from the resolved config, not merely from evaluation.**
For `layouts`/`filters`/`appenders`, `enabled: false` on a *named* component definition (`layouts.x`, `filters.x`, `appenders.x`) makes `resolve_named()` return `NULL`, and any `appenders:`/`filters:` list entry that references it by name is silently dropped rather than raising an "unknown reference" validation error - referencing a disabled-but-defined component must stay valid so ops can flip the flag without editing every logger that lists it. Inline (unnamed) component defs with `enabled: false` are likewise dropped from whatever list they appear in.
*Alternative considered*: keep `enabled` purely conventional (users wrap the whole block in `${VAR}`-driven YAML anchors or omit it via templating outside `lgr`). Rejected - this is exactly the workaround the reference implementation had to build custom code for (`isEnabled` checks scattered through `config_logging.list()`), and env-var interpolation already makes `enabled: ${ELASTIC_ENABLED:-false}` natural once `enabled` is a recognized key.

**`enabled: false` on a logger definition fully resets that logger, it does not skip it.**
A disabled logger SHALL end up in the exact same state as one that was never configured at all (as if `lg$config(NULL)` had been called on it): no custom threshold, no appenders, no filters, `propagate = TRUE`, default `exception_handler`. This is a deliberate departure from "absent from `loggers:` = untouched": a logger *named in the config with `enabled: false`* is an explicit statement of intent ("this logger must not run"), and honoring that intent only if the logger happened to be unconfigured before would make the outcome depend on apply-order history rather than on the config alone. Resetting on every application makes the config idempotent for that logger: applying the same config twice, or applying it after any prior state, always yields the same end state. This mirrors what `disable_existing_loggers: true` already does for *unlisted* loggers - `enabled: false` is simply the per-logger, always-listed equivalent.
*Alternative considered*: skip the logger entirely, leaving it in whatever state it already had (the original plan). Rejected - it breaks idempotency (result depends on load history) and doesn't match the intuitive meaning of "disabled": a disabled logger should not exist/run, not "whatever it happened to be already."

**`FilterInjectSystemInfo` is a new class using the existing `class:`-based extension mechanism, not a config-grammar feature.**
It inherits `FilterInject` and, in `initialize()`, computes a fixed set of defaults exactly once (construction time, same timing `FilterInject` already has) - `hostName` (`Sys.info()[["nodename"]]`) and `rVersion` (`R.Version()$version.string`) unconditionally; `containerId` (`Sys.info()[["nodename"]]` again, matching the reference implementation's convention that the container's own hostname *is* its id) only when a Docker container is detected (`file.exists("/.dockerenv")`); `scriptFile` when determinable by the same detection chain `get_current_scriptfile()` already uses (RStudio API → `Rscript`/`R --file` `commandArgs()` → `sys.calls()` for `source()`), omitted (not set to `NA`/`""`) when none of those apply. It then merges any `...`/`.list` args supplied by the caller on top of these defaults (explicit values override same-named defaults) and delegates to `FilterInject$initialize()` for the rest - so the per-event injection behavior (loop over a snapshotted `values` list) is inherited unchanged. This lives in lgr core (not `lgrExtra`): unlike the ElasticSearch/Dynatrace appenders, it needs no heavy external dependency - only base R plus an optional `rstudioapi` (`Suggests`, degrades gracefully if absent, consistent with how `yaml`/`jsonlite` are already handled).
*Alternative considered*: extend `FilterInject` itself with a `system_info = TRUE` flag. Rejected - it would make one class do two different, independently-toggleable things (arbitrary literal injection vs. built-in runtime-metadata injection), whereas a separate class keeps each existing option meaning exactly one thing: `FilterInject` for values you provide, `FilterInjectSystemInfo` for the standard bundle (still extensible with your own values on top).
*Alternative considered*: fold deployment-tool-specific env vars (like a release id) into `FilterInjectSystemInfo` itself. Rejected - vendor/deploy-tool-specific names don't belong in a general-purpose logging package; `"${RELEASE_ID:-}"` already works via ordinary interpolation on any `FilterInject`/`FilterInjectSystemInfo` argument, so there is nothing left to build for that part.

**Validate the production-equivalent config through an integration test with the real `lgrExtra::AppenderDynatrace`, gated the same way existing Dynatrace/ElasticSearch tests are.**
`tests/testthat/test_logging_config.R` already exercises `lgrExtra` under `Suggests`. The new fixture config (console + file + Dynatrace) lives alongside it and is applied via `read_config()`/`Logger$config()`, asserting the resolved logger tree matches what `config_logging()` would have built (same appender classes, thresholds, layout/transform, injected filter values) - without needing a live Dynatrace endpoint, since appender construction itself (not network I/O) is what's under test.

## Risks / Trade-offs

- [Risk] Widening function-value resolution to arbitrary args could let a `ref:`/`code:` payload sneak into a slot nobody intended to be dynamic, obscuring config validation errors. → Mitigation: the shape stays opt-in (`{ref:...}`/`{code:...}` mapping only, no bare-string coercion outside filter context), and `code:` remains gated by `allow_code` regardless of position, per the existing safety rules.
- [Risk] `enabled: false` on a referenced-but-not-yet-defined component could mask genuine typos (a truly unknown reference vs. an intentionally disabled one look similar once the "unknown reference" error is relaxed). → Mitigation: disabling still requires the component to be *defined* under `layouts`/`filters`/`appenders` with `enabled: false`; a reference to a name that doesn't exist in those sections at all continues to be a hard validation error.
- [Risk] The production-equivalent fixture config drifts from the real production config over time (they live in different repos). → Mitigation: treat the fixture as a point-in-time acceptance test, not a synced copy; call this out in the test file's comment.
- [Risk] `scriptFile`/`hostName`/`containerId` detection is inherently environment-dependent (CI runners, containers without `/.dockerenv` conventions, non-interactive `Rscript` invocations) and can't be exhaustively tested. → Mitigation: tests assert presence/absence and type of each field under mockable conditions (e.g. stub `file.exists("/.dockerenv")`), not exact values; document that fields are best-effort and silently omitted, never erroring, when undeterminable.

## Migration Plan

Not applicable - this is an additive change to `lgr`'s config loader (new optional `enabled` key, widened function-value resolution) with no breaking changes to the existing format. No migration of existing configs is required. Two things are explicit follow-up work outside this change: (1) the originating production system migrating off `config_logging()` onto native `lgr` config, and (2) extending `lgrExtra::AppenderElasticSearch` to accept primitive connection arguments (e.g. `host`) so `conn` no longer requires a pre-built connection object - needed before ElasticSearch can be added to the acceptance fixture.
